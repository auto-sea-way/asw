# asw-mobile — the planet graph on a phone

- **Date:** 2026-09-28
- **Status:** design approved in brainstorming, awaiting spec review
- **Driver:** a mobile app needs offline sea routing and an on-water test from the v4
  planet graph file, called from a background relaunch with a budget of a few seconds and
  a few megabytes of resident memory.
- **Builds on:** `docs/superpowers/specs/2026-09-27-graph-format-v4-design.md` (the file
  format and `asw-core` this crate wraps).

## 1. Scope

A new crate `crates/asw-mobile` that exposes four operations over `asw-core` through a
foreign-function interface, packaged as an iOS xcframework and an Android AAR and attached
to every GitHub release next to the binaries and the graph file.

In scope: the crate, its Swift and Kotlin bindings, packaging, CI, tests, a README.

Out of scope: downloading and storing the graph file on the phone, a manifest, region
support (the whole planet ships as one file), a `Package.swift` or Maven publication in
this repo, the on-device smoke test. Those belong to the consuming app.

## 2. Decisions

- Bindings are generated by UniFFI from proc-macro annotations on the Rust code. No
  interface definition file, no hand-written C ABI.
- `route` takes a shore buffer in nautical miles, validated to 0 to 5 like the HTTP API.
  No cancellation or time budget: consecutive fixes make short routes; add a budget only
  when a measured case needs one.
- The AAR is attached to the GitHub release; the consuming app fetches it for its pinned
  version with a Gradle task. No GitHub Packages, no Maven Central.
- One Android ABI, `arm64-v8a`; two iOS slices, device and simulator, both arm64.
- Panics never cross the boundary.
- The crate does not name any consuming app anywhere.

## 3. API

Module names: Swift `AswMobile`, Kotlin package `org.autoseaway.mobile`.

```
open_graph(path: String) -> Result<Graph, AswError>
    Memory-map the file and validate the header. Milliseconds, a few pages.
    (Named open_graph: `open` needs backticks in both Swift and Kotlin.)

Graph.version() -> String
    The version string stored in the file header, e.g. "0.7.0 2026-09-27".

Graph.is_water(lat: f64, lon: f64) -> Water
    Water | Land | Unknown. Snap to the nearest water node and count coastline
    crossings on the way to the point (asw_core::routing::is_water). No node within
    the snapping ladder is Land. Unknown when the coordinates are invalid or the
    call panics (section 4). A file changed in place under the mapping raises a bus
    error that nothing can catch; the app must replace the file by atomic rename.

Graph.route(from_lat, from_lon, to_lat, to_lon: f64, shore_buffer_nm: f64)
    -> Result<Route, AswError>
    asw_core::routing::compute_route with the graph's own nearest_node and coastline.

Route { coordinates: Vec<Coordinate>, distance_nm: f64, land_legs: Vec<u32> }
Coordinate { lat: f64, lon: f64 }
    Same semantics as the HTTP /route response: coordinates start and end at the
    requested points, distance_nm counts water segments only, land_legs are indices of
    segments that cross land.

AswError { NotFound, BadFormat(detail), InvalidArgument(detail), NoRoute,
           Internal(detail) }
    (`detail`, not `message`: the generated Kotlin exception would clash with
    Throwable.message.)
```

`Graph` is a UniFFI object: reference counted, `Send + Sync`, holding the mapped
`RoutingGraph` and `Mutex<Option<AstarBuffers>>`, the buffer set created on the first
route. `is_water` needs no buffers.

## 4. Errors and panics

Every exported function body runs inside `std::panic::catch_unwind` (with
`AssertUnwindSafe` around the graph reference). A panic in `open` or `route` becomes
`AswError::Internal` carrying the panic message; a panic in `is_water` becomes `Unknown`.
This covers the corrupt-but-well-formed file case the v4 review noted (a bad H3 id or a
non-monotonic offsets table panics at query time in `asw-core`).

`open`: a missing or unreadable file is `NotFound`; a file that `RoutingGraph::open`
rejects (wrong magic, v3, truncated, bad section table) is `BadFormat` with the reader's
message. `route`: a shore buffer outside 0 to 5 nm or a non-finite coordinate is
`InvalidArgument`; no path is `NoRoute`. The app never sees an abort.

## 5. Memory and threading

- `open` reads the header, the section table and the three CSR sentinels: O(1) in the
  node count, well under 10 ms on a phone from flash. `RoutingGraph::open(path, false)`
  skips the monotonicity scans over the coastline and grid tables (26 MB of pages);
  the server, with `populate = true`, keeps them.
- `is_water` touches the node index (binary search over the sorted ids, a few pages),
  one or a few 0.1° grid cells and the coastline runs they list: tens of kilobytes
  resident per call.
- `route` allocates the A* buffers on first use; they are zero-filled (`calloc`, lazy
  pages) and 33 bytes per node of virtual memory, resident only where the search
  touches. A route between two fixes minutes apart touches a few hundred kilobytes; a
  transoceanic route tens of megabytes.
- Mapped file pages are clean and evictable; on iOS they do not count against the jetsam
  limit the way heap does.
- All calls are synchronous and safe from any thread. Routes serialise on the single
  buffer set (`ponytail:` one set per Graph; a pool if a phone ever routes concurrently).
  `is_water` calls run concurrently without locking.

## 6. Packaging

**iOS.** Rust targets `aarch64-apple-ios` and `aarch64-apple-ios-sim`, deployment target
iOS 17, crate type `staticlib`. `uniffi-bindgen generate --library` produces the C
header, module map and `AswMobile.swift`. `xcodebuild -create-xcframework` combines the
two slices and the headers into `AswMobile.xcframework`. Release asset:
`AswMobile-<version>.zip` containing the xcframework and `AswMobile.swift`. The consuming
app declares a binary target with the asset URL and checksum and adds the Swift file to
its target.

**Android.** Rust target `aarch64-linux-android`, crate type `cdylib`, minSdk 21, linked
with `-Wl,-z,max-page-size=16384` for Android 15 devices. `cargo-ndk` writes
`jniLibs/arm64-v8a/libasw_mobile.so`; `uniffi-bindgen` writes the Kotlin source; a
minimal Gradle library project in `crates/asw-mobile/android/` compiles both into
`asw-mobile-<version>.aar`. The generated Kotlin depends on JNA
(`net.java.dev.jna:jna:<version>@aar`), which the consuming app adds next to the AAR.

Both assets and their checksums join the existing `SHA256SUMS`.

## 7. CI and release

- `ci.yml`: build and test `asw-mobile` on the host; run `uniffi-bindgen` for Swift and
  Kotlin on the host library and type-check the outputs (`swiftc -typecheck` on macOS,
  `kotlinc` on Ubuntu), so a binding break fails the PR, not the release.
- `release.yml`: a new `mobile` job with two runners, `macos-latest` for the xcframework
  and `ubuntu-latest` for the AAR (NDK and Android SDK are preinstalled). Their artefacts
  are collected by the existing `release` step. One tag carries the four binaries, the
  graph, the xcframework zip, the AAR and one checksum file.
- The crate version is the workspace version; the bindings, the crate and the graph
  file share the release number.

## 8. Testing

- Rust unit tests in `crates/asw-mobile/src/lib.rs` on a builder-made graph written to
  a temporary file: `open` + `version`; `is_water` water, land and behind-a-mole (parity)
  cases; `route` with buffer 0 and 0.5; `NoRoute`; `InvalidArgument` for a 6 nm buffer;
  `NotFound`; `BadFormat` for a v3 magic; a test-only hook that forces a panic in
  `route` and `is_water` to prove `Internal` and `Unknown`.
- Binding compile checks in CI (section 7).
- Planet numbers measured once on Linux with the release graph and written into
  `crates/asw-mobile/README.md`: open time; resident memory after `is_water`, after a
  short route, after a transoceanic route.
- The on-device smoke test is the consuming app's.
